## Overview

werf supports the following build backends:

-	Docker — the traditional method that uses the system Docker Daemon.
-	Buildah — a secure, daemonless build option that supports rootless mode and is fully embedded into werf.

> The requirements and system preparation steps for using these build backends are described in the [Getting Started]({{ site.url }}/getting_started/) section of the website.

## Docker

The Docker backend requires Docker 19.03 or newer (Engine API 1.40 or newer) for building or running containers. Commands that need the backend reject an older daemon API or a daemon that does not answer within 10 seconds. A daemon that is not running is tolerated during initialization; an operation that actually needs it will still fail.

`werf converge`, `werf plan`, `werf render`, `werf lint`, `werf helm get-autogenerated-values`, and `werf bundle publish` initialize the backend only when processing images. Projects without images and `--without-images` do not need a Docker daemon. `werf plan`, `werf render`, `werf lint`, and `werf helm get-autogenerated-values` also skip initialization with `--stub-tags` or a local repository address. `werf converge --use-plan` and `werf plan --show-plan` do not need the backend either. Image-processing paths retain the daemon API and response checks, including `--require-built-images` and `--use-build-report`.

Commands that only work with a container registry (`werf cleanup`, `werf purge`, `werf dismiss`, `werf managed-images`, `werf meta-repo`) tolerate old, missing, and unresponsive Docker daemons. Daemon-provided registry settings are skipped when the daemon API is unsupported, when the daemon host does not resolve, when the connection is refused or the host or network is down or unreachable, when the socket or named pipe does not exist, and when the daemon accepts the connection but never answers. Everything else propagates: a socket the current user may not open, authentication and authorization failures, TLS errors, HTTP errors, malformed or non-Engine API responses, and unexpected server errors. These commands may trigger automatic host cleanup, which does use the daemon. Failure of that cleanup does not affect the command's own result.

Over `ssh://`, the pinned Docker client can normalize some remote Unix-socket failures, including permission denial, into the same generic "cannot connect" error as a missing socket. This inherited limitation means optional settings discovery may skip a remote permission failure as an unavailable daemon. Failures of the `ssh` command itself remain distinguishable: refused, down, unreachable, timed-out or unresolvable SSH hosts are skipped, while SSH authentication denial, local socket permission errors and a remote host without the Docker CLI still propagate.

## Buildah

> Currently, Buildah is available only for Linux users and Windows users with WSL2 enabled. For macOS users, it is recommended to use a virtual machine to run werf in Buildah mode.

Buildah can be enabled by setting the environment variable `WERF_BUILDAH_MODE` to one of the following:

* auto — automatic mode selection based on the platform and environment.
*	native-chroot — uses chroot isolation for build containers.
*	native-rootless — uses rootless isolation for build containers. At this level, werf utilizes a container runtime for build operations (e.g., runc, crun, kata, or runsc).

```shell
export WERF_BUILDAH_MODE=auto
```

### Network tools

`netavark` must be in one of `/usr/local/libexec/podman`, `/usr/local/lib/podman`, `/usr/libexec/podman`, `/usr/lib/podman` — `$PATH` is not searched. `pasta` is found in these directories or via `$PATH`.

If werf and system Podman/Buildah share storage, check their network settings separately, including `${graphroot}/defaultNetworkBackend`: upgrading werf does not migrate the system CLI configuration from CNI to netavark.

### Container registry configuration

When using Buildah, werf reads container registry settings from `registries.conf`.

For secure `docker.io` mirrors, you can also use the `--container-registry-mirror` option and `WERF_CONTAINER_REGISTRY_MIRROR_*` environment variables. Mirrors configured this way are treated as secure (`https`) mirrors by default. If needed, you can enable werf global insecure mode for registry access with `--insecure-registry` or `--skip-tls-verify-registry`.

The following paths are supported in priority order:

1. the path from `CONTAINERS_REGISTRIES_CONF`;
2. `~/.config/containers/registries.conf`;
3. `/etc/containers/registries.conf`.

If `CONTAINERS_REGISTRIES_CONF` is set, werf uses only that file and its neighboring `<path>.d` directory.

If `CONTAINERS_REGISTRIES_CONF` is not set, werf uses the first existing file from the standard paths and the neighboring `<path>.d` directory for that file.

werf uses the following data from this configuration:

- mirrors for `docker.io`;
- standalone insecure registries from `[[registry]] insecure = true`.

werf does not parse or override other container configuration files such as `shortnames.conf`.

An insecure mirror for `docker.io` does not automatically make the same host a standalone insecure registry. If the same host must be used both as a `docker.io` mirror and as a standalone insecure registry, it must be described by two separate entries.

### Storage Driver

werf can use either the `overlay` or `vfs` storage driver:

* `overlay`: Uses the OverlayFS file system. Either kernel-integrated OverlayFS support (if available) or the fuse-overlayfs implementation can be used. This is the recommended default option.
* `vfs`: Provides access to a virtual file system instead of OverlayFS. This option has lower performance and requires a privileged container, so it is not recommended. However, it may be useful in some cases.

In general, the default driver (`overlay`) should suffice. The storage driver can be specified using the environment variable `WERF_BUILDAH_STORAGE_DRIVER`.

### Ulimits

By default, Buildah mode in werf inherits the system ulimits when launching build containers. Users can override these parameters using the `WERF_BUILDAH_ULIMIT` environment variable.

Format: `WERF_BUILDAH_ULIMIT=type:softlimit[:hardlimit][,type:softlimit[:hardlimit],...]` — a comma-separated list of limits:

* `core`: maximum core dump size (ulimit -c).
* `cpu`: maximum CPU time (ulimit -t).
* `data`: maximum size of a process's data segment (ulimit -d).
* `fsize`: maximum size of new files (ulimit -f).
* `locks`: maximum number of file locks (ulimit -x).
* `memlock`: maximum amount of locked memory (ulimit -l).
* `msgqueue`: maximum amount of data in message queues (ulimit -q).
* `nice`: niceness adjustment (nice -n, ulimit -e).
* `nofile`: maximum number of open files (ulimit -n).
* `nproc`: maximum number of processes (ulimit -u).
* `rss`: maximum size of a process's resident set size (ulimit -m).
* `rtprio`: maximum real-time scheduling priority (ulimit -r).
* `rttime`: maximum real-time execution between blocking syscalls.
* `sigpending`: maximum number of pending signals (ulimit -i).
* `stack`: maximum stack size (ulimit -s).

## Layer compression

Image layers that werf publishes to the container registry are compressed with gzip at the compressor's default level. The compression can be changed for all images or for a particular image:

* `--compression-format` (`$WERF_COMPRESSION_FORMAT`) and `--compression-level` (`$WERF_COMPRESSION_LEVEL`) of the commands that build images apply to every image;
* the `build.compression` directive of the werf.yaml meta section applies to every image and takes precedence over the command-line options;
* the `compression` directive of an image takes precedence over both and replaces them as a whole: a level set for all images does not carry over to an image with its own format.

```yaml
project: models
configVersion: 1
build:
  compression:
    format: zstd
    level: 19
---
image: weights-streamed
dockerfile: Dockerfile.weights
compression:
  format: none
```

The available formats:

* `gzip` (default): levels `0`-`9`, the Docker image format;
* `zstd`: levels `1`-`22`, the OCI image format with the `application/vnd.oci.image.layer.v1.tar+zstd` layers;
* `none`: uncompressed layers, the OCI image format with the `application/vnd.oci.image.layer.v1.tar` layers; no level.

If the level is omitted, the default level of the format is used. For `gzip`, level `0` produces a gzip stream without compression, not an uncompressed layer: the layer media type stays gzip.

Whether a format pays off depends on the layer contents and on the consumers: `zstd` saves registry space and download time at the cost of decompression CPU, `none` avoids decompression entirely at the cost of space and traffic. Measure your own images before switching.

### Cache

A compression other than gzip at the default level is part of the stage digests: stages of an image with such a compression are built and published separately from the stages of images with other settings, and changing the compression of an image rebuilds its stages. Images without compression settings keep their digests and their cache.

All layers of such an image, including the layers of its base image, are published with the selected format: layers that the container registry already has in another format are compressed anew instead of being reused.

### Container backends

With Buildah, layers are compressed when the image is published.

With Docker, layers are compressed when the image is built, so the Docker daemon has to use the [containerd image store](https://docs.docker.com/engine/storage/containerd/). With the classic image store, which always publishes gzip layers, werf fails before building an image that has compression settings. Stapel images do not support compression settings with Docker: werf fails before building them.

With the containerd image store, an image built without compression settings keeps the daemon default: BuildKit may reuse a zstd or uncompressed variant of a layer that the daemon already has for another image. Set `format: gzip` for images that must be published with gzip layers on such a daemon.

### Compatibility

`zstd` and `none` layers require the OCI image format. Before switching, verify that the container registry, registry proxies, and every container runtime and tool that pulls these images accept OCI manifests and these layer media types. There is no fallback: if the registry rejects them, publishing fails.

The OCI image format has no `HEALTHCHECK`, `ONBUILD` or `SHELL` image config fields. Rather than dropping them silently, werf with Buildah refuses to publish an image that uses any of them with the `zstd` or `none` format, naming the fields and the image in the error. Use `gzip` for such images.

`zstd` and uncompressed layers cannot be written into a docker archive: the archive format records every layer as gzip. werf therefore rejects writing such an image to a docker archive with `werf stages copy --to archive:PATH`. Copying between container registries is not affected.
