---
title: Миграция с v2 на v3

Изменения v3 сгруппированы по месту настройки: `werf.yaml`, сборка и CI, деплой. Удалённые возможности требуют изменений до обновления; устаревшие ключи пока работают с предупреждением.

## Конфигурация сборки — werf.yaml

### Образы вместо artifacts

Директива `artifact` удалена. Замените её на `image` с `final: false`:

**Было — v2:**

```yaml
artifact: builder
from: ubuntu:22.04
```

**Стало — v3:**

```yaml
image: builder
from: ubuntu:22.04
final: false
```

Безымянные stapel-образы (`image: ~`) больше не поддерживаются — задайте каждому образу имя.

Имена теперь проверяются при загрузке конфигурации. Допустимы латинские буквы, цифры, `_`, `.`, `-` и `+`, а также сегменты через `/`. Каждый сегмент должен начинаться с буквы или цифры и заканчиваться буквой, цифрой или `+`. Имя `modules/controller` допустимо; пустое имя, пробелы, `/api`, `api-` и `modules//controller` вызывают ошибку конфигурации. Проверьте также имена, формируемые Go-шаблонами.

### Ссылки на образы

Для внутренних ссылок используйте единый ключ `from`:

| Где | Было — v2 | Стало — v3 |
|---|---|---|
| Базовый образ stapel | `fromImage: base` | `from: base` |
| Элемент `import` | `image: builder` | `from: builder` |
| Элемент `dependencies` | `image: backend` | `from: backend` |

Старые ключи **не удалены**, но считаются устаревшими. `fromImage` и `import.image` выводят предупреждение; указание одновременно старого и нового ключа — ошибка. `dependencies.image` также продолжает работать, но для новых конфигураций предпочтителен `dependencies.from`.

**Внешняя ссылка** в базовом `from:` или `import.from` теперь требует явного тега или digest. Например, прежнее неявное `:latest` нужно записать явно:

| Было — v2 | Стало — v3 |
|---|---|
| `from: ubuntu` | `from: ubuntu:latest` |

Вместо `:latest` можно указать нужный тег (`:TAG`) или digest (`@sha256:...`). Внутренним именам образов из `werf.yaml` тег не нужен.

### Билдеры и настройки образа

**Ansible-билдер удалён.** Перепишите шаги `ansible:` с использованием Shell-билдера; прямой замены ключа недостаточно.

**Директива `docker:` удалена.** Перенесите настройки в `imageSpec.config`, преобразовав имена и форматы полей. Например, для фрагмента stapel-образа:

**Было — v2:**

```yaml
docker:
  WORKDIR: /app
  ENV:
    APP_ENV: production
```

**Стало — v3:**

```yaml
imageSpec:
  config:
    workingDir: /app
    env:
      APP_ENV: production
```

Полный набор полей описан в разделе [Настройка спецификации образа]({{ "/usage/build/images.html" | true_relative_url }}).

Переменные `WERF_COMMIT_HASH`, `WERF_COMMIT_TIME_HUMAN` и `WERF_COMMIT_TIME_UNIX` больше не удаляются принудительно при модификации env через imageSpec. Если старый базовый образ всё ещё содержит их, добавьте их явно в `imageSpec.config.removeEnv`.

### Пути и giterminism

- Уберите завершающий слэш в `to:` директив export/import: `to: /usr/sbin/` → `to: /usr/sbin`. Исключение — корень `to: /`. Раньше выводилось предупреждение, теперь конфигурация приводит к ошибке сборки.
- Исправьте неизвестные и опечатанные ключи в `werf-giterminism.yaml`: строгая проверка схемы больше не позволяет молча игнорировать их.

## Сборка и CI

### Какие образы собираются и выводятся

`werf build` и другие команды, запускающие сборку, теперь по умолчанию используют `--final-images-only=true`, как уже делали `converge`, `render`, `export`, `plan`, `lint` и `bundle publish`. «Сиротские» нефинальные образы, на которые не ссылается ни один финальный образ, больше не собираются по умолчанию.

`werf config list` также по умолчанию выводит только финальные образы; его устаревший алиас `--images-only` удалён.

**Чтобы сохранить прежнее поведение:**

```shell
werf build --final-images-only=false
werf config list --final-images-only=false
```

### Кеш и git-патчи

- **Ожидайте одноразовую полную пересборку после обновления.** `WERF_STAGED_DOCKERFILE_VERSION=v1` больше не поддерживается: staged Dockerfile всегда использует код версии v2. Вместе с исправлениями расчёта дайджеста в этом релизе это инвалидирует кеши стадий, собранные до v3.
- **Git-стадии переиспользуются без проверки предков коммитов.** Закешированный коммит больше не обязан быть предком текущего. Переменная `WERF_DISABLE_GIT_COMMIT_ANCESTRY_CHECK` удалена.
- **Git-патчи могут перезаписать изменения команд сборки.** Легаси stapel-билдер больше не использует `git apply`: файл, изменённый предыдущей командой `install`/`beforeSetup`/`setup`, теперь молча перезаписывается вместо ошибки о конфликте.
- Если внешние инструменты разбирают сырой вывод git-патчей werf, учтите удаление строки `index <sha>..<sha>`.
- Если интеграции используют лейбл `werf.io/base-image-id` или поле `Info.ParentID`, обновите их: оба удалены. Отслеживание предков при очистке теперь опирается только на `werf.io/parent-stage-id`.

### Удалённые настройки CI

| Удалено | Что изменить |
|---|---|
| `--synchronization` / `-S`, `WERF_SYNCHRONIZATION` | Убрать из команд и окружения. Замены нет: тег стадии content-addressable, распределённый менеджер блокировок больше не нужен. |
| `--virtual-merge`, `WERF_VIRTUAL_MERGE` | Убрать из команд и окружения. Функциональность virtual merge удалена. |

Подсистема `werf synchronization` и зависимость от публичного `synchronization.werf.io` также удалены. Мигрировать нечего; если вы запускали собственный сервер синхронизации, для werf v3 он больше не нужен.

### Buildah: требования к хосту и сеть

Нативный Buildah-бэкенд перешёл с CNI/slirp4netns на netavark/pasta. До обновления подготовьте хосты:

| Компонент | Где требуется |
|---|---|
| `netavark` | На каждом хосте с Buildah-бэкендом, включая chroot без сетевых инструкций. Без него инициализация бэкенда завершится ошибкой. |
| `pasta` из пакета `passt` | Для rootless-сборки, которая настраивает сеть. Не вызывается при `network: host`, `network: none` и в режиме chroot. |

`netavark` должен находиться в одном из каталогов `/usr/local/libexec/podman`, `/usr/local/lib/podman`, `/usr/libexec/podman`, `/usr/lib/podman` — поиск по `$PATH` не выполняется. Для `pasta` используются эти каталоги и `$PATH`. Официальные Ubuntu-образы werf теперь основаны на Ubuntu 24.04.

**Проверьте настройки сети.** Для нестадийных Dockerfile-сборок на нативном Buildah теперь учитываются `network:` и `--backend-network`; раньше они молча игнорировались. Поддерживаются только `default`, `host`, `none`: `bridge` и имена Docker-сетей теперь вызывают ошибку.

Ограничения и совместимость:

- Для образов с `staged: true` настройка сети уровня образа по-прежнему игнорируется; действует только `RUN --network=` конкретной инструкции.
- В `native-chroot` Buildah принудительно использует хостовую сеть, поэтому `network: none` не обеспечивает изоляцию.
- Поддержка CNI исключена при компиляции и не может быть восстановлена. slirp4netns можно вернуть на отдельном хосте через `CONTAINERS_CONF_OVERRIDE`: `default_rootless_network_cmd="slirp4netns"` в секции `[network]`.
- Это **не миграция конфигурации системного Podman/Buildah**: werf не читает и не перезаписывает `${graphroot}/defaultNetworkBackend`. Если там записано `cni`, значение сохраняется и продолжает влиять на системный CLI, использующий тот же graphroot.

## Деплой

**Перед первым `werf converge` проверьте `werf plan`:** изменения values и правил исключения файлов могут повлиять на манифесты без предупреждения.

### Values и переменные окружения

| Где | Было — v2 | Стало — v3 |
|---|---|---|
| Шаблоны основного чарта и зависимостей | `.Values.global.env` | `.Values.global.werf.env` |
| Выбор хранилища релизов | `HELM_DRIVER` | `WERF_RELEASE_STORAGE` |

Старый ключ `.Values.global.env` может превратиться в пустое значение без ошибки. Для временной совместимости можно задать `WERF_LEGACY_VALUES_GLOBAL_ENV=1`.

Без замены `HELM_DRIVER` werf использует хранилище релизов по умолчанию, а не ранее указанное этой переменной. Переменные путей Helm — `HELM_CACHE_HOME`, `HELM_CONFIG_HOME`, `HELM_DATA_HOME` — продолжают работать.

### Чарты и бандлы

**`.helmignore` теперь действует при чтении чарта.** Исключённые файлы исчезают из сформированных манифестов и публикуемого бандла **без предупреждения**.

- Даже без `.helmignore` правила Helm по умолчанию исключают файлы и директории, начинающиеся с точки, непосредственно в `templates/`. Директории исключаются вместе с содержимым.
- `**` теперь вызывает ошибку, хотя раньше не оказывал эффекта.
- Не используйте ведущий `!` как в `.gitignore`: он не отменяет предыдущие исключения, а исключает всё, что не подошло под маску, как правило оставляя чарт пустым.

Правила для зависимых чартов зависят от способа подключения — см. [Чарты и зависимости]({{ "/usage/deploy/charts.html#исключение-файлов-или-директорий-из-чарта" | true_relative_url }}).

**`werf bundle publish` теперь использует `--helm-compatible-chart=true` по умолчанию.** Имя в `Chart.yaml` публикуемого бандла становится последним компонентом пути репозитория; меняются `.Chart.Name` и пути шаблонов. Чтобы сохранить имя из вашего `Chart.yaml`, передайте:

```shell
werf bundle publish --helm-compatible-chart=false
```

Режим совместимости `AllowMissedSecretKeyMode` из v1.2 удалён. При этом `bundle publish` по-прежнему не требует ключ секретов по умолчанию: значения секретов обрабатываются без расшифровки другим механизмом.

### Зашифрованные секреты

**Старый клиент не сможет прочитать секрет, записанный v3; возможности записать прежний формат нет.** Соблюдайте порядок обновления:

1. Обновите **все** окружения, читающие секреты репозитория, до werf v3 или nelm v2: локальные машины, CI-задачи и задачи, применяющие сохранённые deploy plans.
1. Только после этого создавайте, редактируйте или ротируйте секреты. После перешифрования старый werf или nelm не должен работать с репозиторием.

| Было — v2 | Стало — v3 |
|---|---|
| Секреты в формате AES-CBC | Старые значения продолжают расшифровываться; новые записи используют новый формат. |
| Исходный YAML-тип зашифрованного значения не сохранялся | Для новых YAML-значений сохраняются тип и стиль; повреждённый ciphertext и неверный ключ распознаются. |

Дополнительные условия:

- Ciphertext целого secret-файла по-прежнему можно использовать как значение в `secret-values.yaml`.
- Целые secret-файлы используют формат 2, значения в `secret-values.yaml` — формат 3. Автоматическое различение не даёт интерпретировать целый secret как YAML-метаданные.
- Старые зашифрованные скаляры остаются строками. Чтобы восстановить число, boolean, timestamp или другой тип, введите значение заново через `werf helm secret values edit`.
- **Комментарии у зашифрованных значений сохраняются открытым текстом. Не записывайте в них секреты.**
