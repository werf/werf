## Обратно несовместимые изменения в v3.0

Ключевые изменения:
1. Команда `werf build` (и другие команды, запускающие сборку) теперь по умолчанию используют `--final-images-only=true`, как и `converge`, `render`, `export`, `plan`, `lint`, `bundle publish`. Передайте `--final-images-only=false`, чтобы также собирать «сиротские» нефинальные образы, на которые не ссылается ни один финальный образ.
1. Команда `werf config list` теперь по умолчанию использует `--final-images-only=true`, устаревший алиас `--images-only` удалён. Передайте `--final-images-only=false`, чтобы вернуть прежний вывод.
1. Директива образа `artifact` больше не поддерживается. Используйте `image` с `final: false`.
1. Опция `--synchronization`/`-S` и переменная окружения `WERF_SYNCHRONIZATION` удалены без замены — тег стадии теперь content-addressable, и распределённый менеджер блокировок больше не нужен.
1. Опция `--virtual-merge`/`WERF_VIRTUAL_MERGE` и связанная с ней функциональность удалены.
1. Безымянные stapel-образы (`image: ~`) больше не поддерживаются; задавайте явное имя для каждого образа.
1. Имена образов проверяются при загрузке конфигурации. Имя состоит из латинских букв, цифр, `_`, `.` и `-`, при желании разбитое на сегменты через слэш, и каждый сегмент обязан начинаться и заканчиваться буквой или цифрой. Иерархические имена вида `modules/controller` продолжают работать; а пустое имя, имя с пробелами или с висячим разделителем (`/api`, `api-`, `modules//controller` — как правило, результат отрендерившегося в пустоту Go-шаблона) теперь даёт ошибку конфигурации вместо невнятного отказа позже, на сборке.
1. Поле `image: NAME` директивы `import` в stapel-образах переименовано в `from: NAME`.
1. Внешние ссылки `from:` (базовый образ stapel и `import.from`) теперь обязаны содержать явный тег (`:TAG`) или digest (`@sha256:...`); ссылка без тега — это жёсткая ошибка конфигурации, а не тихое разрешение в `:latest`.
1. `WERF_STAGED_DOCKERFILE_VERSION=v1` больше не поддерживается — staged Dockerfile всегда использует код версии v2. Вместе с сопутствующими исправлениями расчёта дайджеста в этом же релизе это инвалидирует все кеши стадий, собранные до v3 (ожидайте одноразовую полную пересборку после обновления).
1. Валидация схемы `werf-giterminism.yaml` теперь строгая: неизвестные/опечатанные ключи вызывают ошибку валидации вместо того, чтобы молча игнорироваться.
1. Файлы `werf.yaml` с завершающим слэшем в пути `to:` директив export/import (кроме `to: /`) теперь не проходят сборку с ошибкой вместо предупреждения в лог. Уберите завершающий слэш, например `to: /usr/sbin/` → `to: /usr/sbin`.
1. Применение git-патчей в легаси stapel-билдере больше не идёт через `git apply`; файл, изменённый предыдущей командой `install`/`beforeSetup`/`setup`, теперь молча перезаписывается вместо ошибки о конфликте.
1. Режим совместимости `AllowMissedSecretKeyMode` из v1.2 удалён. Команда `bundle publish` по-прежнему не требует ключ секретов по умолчанию (значения секретов теперь обрабатываются другим механизмом, без расшифровки), но старый флаг/поведение совместимости отсутствует.
1. Лейбл образа `werf.io/base-image-id` и соответствующее поле `Info.ParentID` удалены. Отслеживание предков при очистке теперь полагается только на `werf.io/parent-stage-id`.
1. Проверка предков git-коммитов при переиспользовании git-стадий удалена вместе с переменной окружения `WERF_DISABLE_GIT_COMMIT_ANCESTRY_CHECK`: закешированная git-стадия теперь переиспользуется независимо от того, является ли её коммит предком текущего.
1. Команда `werf bundle publish` теперь по умолчанию использует `--helm-compatible-chart=true`: имя чарта в `Chart.yaml` публикуемого бандла становится последним компонентом пути адреса репозитория, из-за чего меняются `.Chart.Name` и пути шаблонов. Передайте `--helm-compatible-chart=false`, чтобы сохранить имя из вашего `Chart.yaml`.
1. Параметр `network:` в `werf.yaml` и флаг `--backend-network` теперь учитываются для нестадийных (non-staged) Dockerfile-сборок на нативном Buildah-бэкенде — раньше они там молча игнорировались. Для образов с `staged: true` настройка уровня образа по-прежнему игнорируется — там действует только флаг `RUN --network=` у конкретной инструкции. Этот бэкенд поддерживает только значения `default`, `host` и `none`, поэтому Docker-значение вроде `bridge` или имя сети теперь приводит к ошибке, а не отбрасывается. Значение `none` по-прежнему невозможно соблюсти в режиме `native-chroot`, поскольку Buildah принудительно использует хостовую сеть для chroot-изоляции.
1. Нативный Buildah-бэкенд теперь использует `netavark` в качестве сетевого бэкенда и `pasta` в качестве rootless-сетевой команды вместо CNI и slirp4netns. Бинарный файл `netavark` должен присутствовать в одном из каталогов вспомогательных бинарных файлов Podman (`/usr/local/libexec/podman`, `/usr/local/lib/podman`, `/usr/libexec/podman` или `/usr/lib/podman`; поиск по `$PATH` не выполняется) на каждом хосте, где werf работает в режиме Buildah, — без него werf завершится с ошибкой при инициализации бэкенда, даже в режиме chroot без сетевых инструкций. Для rootless-сборки, которая настраивает сеть, дополнительно требуется бинарный файл `pasta` из пакета `passt` (ищется в каталоге вспомогательных бинарных файлов или в `$PATH`); при `network: host`, `network: none` и в режиме chroot он не используется, поскольку Buildah настраивает сеть только для сетевого пространства имён, отличного от хостового. Поддержка CNI исключена на этапе компиляции и не может быть восстановлена; slirp4netns больше не используется, но его можно вернуть на отдельном хосте через `CONTAINERS_CONF_OVERRIDE` (конфиг с `default_rootless_network_cmd="slirp4netns"` в секции `[network]`). Явное закрепление сетевого бэкенда обходит `${graphroot}/defaultNetworkBackend`: werf не читает и не перезаписывает этот файл, поэтому хранилище, в котором записан `cni`, сохраняет это значение и продолжает влиять на системный CLI podman или buildah, использующий тот же graphroot. Официальные Ubuntu-образы werf теперь основаны на Ubuntu 24.04.

Прочие изменения:
1. Директива `fromImage` (stapel-образ) и `import: - image:` считаются устаревшими в пользу `from:`; они по-прежнему работают, но выводят предупреждение об устаревании. Указание одновременно старого и нового ключа — жёсткая ошибка.
1. `dependencies.image` считается устаревшей в пользу `dependencies.from`; обе работают, но в новых конфигурациях предпочтительнее `from`.
1. Убрано жёстко закодированное удаление `WERF_COMMIT_HASH`/`WERF_COMMIT_TIME_HUMAN`/`WERF_COMMIT_TIME_UNIX` из логики модификации env в imageSpec. Если ваш базовый образ был собран более старой версией werf и всё ещё содержит эти переменные, добавьте их явно в `imageSpec.config.removeEnv`.
1. Строка `index <sha>..<sha>` убрана из вывода git-патчей. Актуально только если вы разбираете сырой вывод патчей werf во внешних инструментах.
1. Подсистема `werf synchronization` и зависимость от публичного `synchronization.werf.io` удалены; мигрировать нечего, если вы не запускали собственный сервер синхронизации.

## Одновременная работа werf v2 и werf v3 с одним `--repo`, когда v3 использует `--meta-repo`

Эта схема нужна только если werf v3 использует `--meta-repo`. Без него обе версии хранят метаданные в `--repo`, поэтому миграция не нужна.

В werf v2 нет `--meta-repo`: image-metadata, список managed images, метаданные custom-тегов и запись о последней очистке записываются в `--repo`. Чтобы сборки v2 продолжали работать, пока v3 переносит свои метаданные в отдельный репозиторий, перенесите накопленные v2 метаданные перед запуском очистки.

```shell
werf meta-repo migrate --from registry.mycompany.org/project --to registry.mycompany.org/project-meta
werf cleanup --repo registry.mycompany.org/project --meta-repo registry.mycompany.org/project-meta
```

У такой схемы есть ограничения, о которых стоит знать заранее:

- По умолчанию `migrate` удаляет метаданные из источника. Это безопасно для сборок v2: только `cleanup` в v2 использует эти метаданные, чтобы решать, какие стадии удалять.
- Запускать `cleanup` для общего `--repo` может только werf v3. werf v2 принимал бы решения о судьбе стадий по срезу метаданных, который v3 перенёс, и мог бы удалить используемые образы.
- Каждый перенос перечисляет все теги в `--repo` и запрашивает манифест каждого кандидата в метаданные. На большом общем репозитории это заметное количество запросов к registry, вплоть до срабатывания лимитов.
- Не задавайте один и тот же custom-тег (`--add-custom-tag`, `--use-custom-tag`) из обеих версий werf. Сборка v3 записывает алиас в `--repo`, а его метаданные — в `--meta-repo`; последующая сборка v2 перезаписывает запись в `--repo`. `migrate` оставляет запись, уже лежащую в `--meta-repo`, поэтому перевешивание алиаса, сделанное v2, не попадает в метаданные, которые читает werf, и очистка может удалить алиас, указывающий на живую стадию.
