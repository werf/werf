## О бандлах и чартах

Бандл — это способ дистрибуции чарта и связанных с ним образов как единого целого.

Команда `werf bundle publish` собирает образы и публикует их вместе с чартом для дальнейшего развёртывания с werf. При этом для развёртывания доступ к Git-репозиторию приложения больше не потребуется.

Опубликованный чарт — обычный OCI-чарт Helm: исходный чарт как есть плюс директория `.werf-data/` в его корне. В `.werf-data/` хранится всё, что werf добавляет при публикации:

* собранные образы и их теги в виде служебных параметров werf;
* параметры, переданные опциями `--values`, `--secret-values`, `--set*`, `--set-root-json`, и файлы `--patches`;
* пользовательские и служебные аннотации и лейблы для добавления в ресурсы чарта;
* имя релиза и Namespace, вычисленные для окружения.

`werf bundle apply` (а также `werf bundle plan` и `werf bundle render`) использует всё это, поэтому публикация и последующее применение чарта развёртывают то же самое, что `werf converge` с теми же опциями. Helm, Argo CD, Flux и другие решения тоже могут установить чарт, но по умолчанию получают только собственные параметры чарта, см. [Использование чарта с Helm, Argo CD и Flux](#использование-чарта-с-helm-argo-cd-и-flux).

Опубликованный бандл (чарт и связанные с ним образы) можно копировать в другой репозиторий container registry или выгружать в/из архива с помощью одной команды `werf bundle copy`.

## Публикация бандла

Опубликовать бандл в OCI-репозиторий можно следующим способом:

1. Создайте `werf.yaml`, если его ещё нет:

   ```yaml
   # werf.yaml:
   project: mybundle
   configVersion: 1
   ```

2. Разместите файлы в директории основного чарта (по умолчанию `.helm` в корне Git-репозитория). Публикуются все файлы директории чарта, кроме исключённых `.helmignore` (см. [ниже](#исключение-файлов-или-директорий-из-чарта)).

3. Следующей командой опубликуйте бандл. Соберите и опубликуйте описанные в `werf.yaml` образы (если таковые есть), затем опубликуйте содержимое `.helm` в виде чарта `example.org/bundles/mybundle` с тегом `latest`:

   ```shell
   werf bundle publish --repo example.org/bundles/mybundle
   ```

## Содержимое опубликованного чарта

Директория чарта публикуется как есть: werf ничего не добавляет в `values.yaml`, а `secret-values.yaml` и директория `secret/` чарта остаются на своих местах в зашифрованном виде. В `Chart.yaml` werf меняет только следующие поля, сохраняя остальное содержимое файла, включая комментарии и порядок ключей:

* `name` — последний компонент пути репозитория (см. [Имя и версия чарта](#имя-и-версия-чарта));
* `version` — версия, полученная из тега;
* `appVersion` — только если она задана в `werf.yaml`;
* аннотацию `helm.sh/images` — собранные werf образы и ссылки на них, добавленные к записям, которые указал автор чарта. Если имя записи автора совпадает с именем образа werf, публикация завершается ошибкой: удалите запись из `Chart.yaml` или переименуйте образ werf.

Также werf помещает в `charts/` зависимые чарты, перечисленные в `Chart.lock`, и собирает TypeScript-чарты.

Всё, что werf добавляет при публикации, попадает в `.werf-data/`:

```
.werf-data/
  metadata.yaml        # версия формата (apiVersion: v2), опции --set*, аннотации, лейблы, имя релиза и Namespace
  values.yaml          # файлы --values, объединённые по порядку
  secret-values.yaml   # файлы --secret-values, объединённые по порядку, в зашифрованном виде
  extra-values.yaml    # служебные параметры werf: образы, репозиторий, окружение, коммит
  set-files/0, 1, ...  # содержимое файлов --set-file
  patches/0, 1, ...    # файлы --patches
```

`.werf-data/` всегда публикуется и сохраняется при распаковке и повторной упаковке чарта, даже если её исключает `.helmignore` чарта.

> **Примечание**: `.werf-data/values.yaml`, файлы `set-files/` и строки `--set*` хранятся в registry в открытом виде. Передавайте секреты только через `--secret-values`: werf проверяет, что все значения в этих файлах зашифрованы, и хранит их в зашифрованном виде.

## Публикация нескольких бандлов из одного Git-репозитория

Разместите `.helm` с содержимым чарта и соответствующий ему `werf.yaml` в отдельную директорию для каждого бандла:

```
bundle1/
  .helm/
    templates/
    # ...
  werf.yaml
bundle2/
  .helm/
    templates/
    # ...
  werf.yaml
```

Теперь опубликуйте каждый бандл по отдельности:

```shell
cd bundle1
werf bundle publish --repo example.org/bundles/bundle1

cd ../bundle2
werf bundle publish --repo example.org/bundles/bundle2
```

## Исключение файлов или директорий из чарта

Файл `.helmignore` чарта фильтрует публикуемый чарт так же, как любой чарт, который читает werf, см. [Исключение файлов или директорий из чарта]({{ "/usage/deploy/charts.html#исключение-файлов-или-директорий-из-чарта" | true_relative_url }}).

Опции `--disable-default-values` и `--disable-default-secret-values` команды `werf bundle publish` сохраняются в чарте: `werf bundle apply` тогда игнорирует `values.yaml` и `secret-values.yaml` чарта, как это делает `werf converge` с этими опциями. Сами файлы остаются в чарте, и Helm по-прежнему использует `values.yaml`.

## Использование произвольных тегов образов

Для использования произвольных тегов образов для бандлов необходимо задать шаблон именования с помощью опции `--use-custom-tag` (`WERF_USE_CUSTOM_TAG`).

Пример использования:
```shell
werf bundle publish --repo example.org/bundles/mybundle --use-custom-tag "%image%-my-custom-tag"
```

Подробнее про кастомные теги можно прочитать в [документации]({{ "/usage/build/process.html#добавление-произвольных-тегов" | true_relative_url }}).

## Имя и версия чарта

Имя чарта — всегда последний компонент пути репозитория, в который публикуется чарт: `werf bundle publish --repo example.org/bundles/mybundle` публикует чарт `mybundle`. Helm находит OCI-чарт только в репозитории, названном по имени чарта.

По умолчанию чарт публикуется с тегом `latest`. Указать иной тег, например, семантическую версию, можно опцией `--tag`:

```shell
werf bundle publish --repo example.org/bundles/mybundle --tag v1.0.0
```

Версия чарта определяется по тегу:

* строгая семантическая версия (`MAJOR.MINOR.PATCH` с необязательными prerelease и build, с необязательным префиксом `v`) используется как есть, без префикса `v`: `v1.0.0` → `1.0.0`;
* любой другой тег (`latest`, SHA коммита, имя ветки, `1.2`, число вроде даты или ID пайплайна) получает версию `0.0.0-<unix-время>-<slug тега>`, где slug — тег в нижнем регистре, в котором каждая последовательность символов, кроме букв и цифр, заменена на `-`: `feature/Foo_1` → `0.0.0-<unix-время>-feature-foo-1`.

werf публикует чарт с тегом его версии и, если он отличается, ещё и с указанным тегом, заменяя в обоих `+` на `_`, как это делает Helm: `--tag 1.0.0+build.5` публикует `1.0.0_build.5`. Команда выше публикует `example.org/bundles/mybundle:1.0.0` и `example.org/bundles/mybundle:v1.0.0`, оба указывают на один и тот же чарт.

Версия `0.0.0-…` — это prerelease, поэтому Helm, Argo CD и Flux пропускают её при выборе версии по semver-диапазону: чтобы её выбрать, используйте диапазон вида `>=0.0.0-0` или опцию Helm `--devel`. Две публикации с не-semver тегом в пределах одной секунды получают одинаковую версию и перезаписывают друг друга. Такие версии накапливаются в registry: очистка werf их не удаляет.

Если при публикации будет обнаружено, что в OCI-репозитории уже существует чарт с таким тегом, то чарт в репозитории будет перезаписан.

## Развёртывание бандла

`werf bundle apply` развёртывает опубликованный чарт без доступа к Git-репозиторию приложения:

```shell
werf bundle apply --repo example.org/bundles/mybundle --tag v1.0.0
```

`werf bundle publish` и последующий `werf bundle apply` развёртывают то же самое, что `werf converge` с опциями, переданными `werf bundle publish`, а `werf release get --print-values` показывает те же параметры. Опции, переданные `werf bundle apply` (`--values`, `--secret-values`, `--set*`, `--set-root-json`, `--patches`, `--add-annotation`, `--add-label`), применяются поверх сохранённых при публикации и имеют приоритет над ними. Параметры объединяются в следующем порядке, от низшего приоритета к высшему:

1. `values.yaml` и `secret-values.yaml` чарта.
2. Опции `--values`, `--secret-values`, `--set*` и `--set-root-json` команды `werf bundle publish`.
3. Служебные параметры werf, вычисленные при публикации (образы, репозиторий, окружение, коммит).
4. Опции `--values`, `--secret-values`, `--set*` и `--set-root-json` команды `werf bundle apply`.
5. Служебные параметры werf, вычисленные при развёртывании (окружение, Namespace и другие).

Файлы `--patches` применяются в том же порядке: собственный `patches.yaml` чарта, затем файлы `werf bundle publish`, затем файлы `werf bundle apply`. Опции `--disable-default-values` и `--disable-default-secret-values` команды `werf bundle apply` игнорируют только `values.yaml` и `secret-values.yaml` чарта, но не параметры, сохранённые при публикации.

`--secret-values` команды `werf bundle publish` расшифровываются при развёртывании и сохраняются в релизе в расшифрованном виде, так же как `werf converge` сохраняет свои `--secret-values`, см. [Секретные параметры в релизе]({{ "/usage/deploy/values.html#секретные-параметры-в-релизе" | true_relative_url }}). Для их расшифровки нужен секретный ключ, которым они были зашифрованы при публикации.

`werf bundle publish` сохраняет имя релиза и Namespace, вычисленные так же, как их вычисляет `werf converge` для указанного `--env`. `werf bundle apply`, `werf bundle plan` и `werf bundle render` используют их вместо непереданных `--release` и `--namespace`, в том числе когда не передан `--env`. Если вы передаёте непустой `--env`, отличный от использованного при публикации, сохранённые значения не используются и обязательны оба флага, `--release` и `--namespace`.

Единственное известное отличие от `werf converge` — `.Chart.Name` и `.Chart.Version`: при `werf converge` шаблоны получают имя проекта и версию из `Chart.yaml` (по умолчанию `1.0.0`), а при `werf bundle apply` — имя репозитория и версию, полученную из тега. Поэтому лейбл вида {% raw %}`helm.sh/chart: {{ .Chart.Name }}-{{ .Chart.Version }}`{% endraw %} различается, и переход релиза с `werf converge` на `werf bundle apply` один раз перезапускает его Pod'ы.

`werf converge`, `werf plan`, `werf render` и `werf lint` тоже используют `.werf-data/`, если находят её в директории чарта (например, если в `.helm` лежит распакованный опубликованный чарт): её параметры, аннотации и лейблы применяются ниже опций команды.

## Использование опубликованного чарта как зависимого

Когда werf или Nelm развёртывает чарт, который подключает опубликованный werf чарт как зависимый, параметры из `.werf-data/` зависимого чарта становятся его параметрами по умолчанию, как если бы он развёртывался сам по себе с `werf converge`. Родительский чарт переопределяет их как обычно. Секретные параметры зависимого чарта расшифровываются секретным ключом развёртывания и, как параметры из `secret-values.yaml` любого зависимого чарта, сохраняются в релизе в расшифрованном виде. Его аннотации и лейблы игнорируются с предупреждением: их определяет родительский чарт.

## Изменение опубликованного чарта

Опубликованный чарт можно скачать, изменить и опубликовать снова без Git-репозитория приложения, например, с помощью CLI [Nelm](https://github.com/werf/nelm):

1. Скачайте и распакуйте чарт:

   ```shell
   nelm chart download oci://example.org/bundles/mybundle --version 1.0.0 --untar
   ```

2. Измените чарт: `values.yaml`, секреты (`nelm chart secret values-file edit mybundle/secret-values.yaml` или `mybundle/.werf-data/secret-values.yaml`), шаблоны или любой файл в `.werf-data/`.

3. Упакуйте чарт и загрузите его:

   ```shell
   nelm chart pack mybundle --set replicas=3
   nelm chart upload mybundle-1.0.0.tgz oci://example.org/bundles
   ```

`nelm chart pack` сохраняет версию из `Chart.yaml`, если не передан `--version`. Опции `--values`, `--secret-values`, `--set*`, `--set-root-json` и `--patches` команды `nelm chart pack` добавляются поверх сохранённых в `.werf-data/`, как если бы их дописали в конец исходной команды `werf bundle publish`: файлы параметров объединяются поверх сохранённых, опции `--set*`, `--set-root-json` и `--patches` добавляются после сохранённых, а новые аннотации и лейблы имеют приоритет над сохранёнными с теми же ключами. Опция `--reset-values` удаляет всё сохранённое в `.werf-data/` перед применением опций этой упаковки. Чтобы удалить одну сохранённую опцию, отредактируйте `.werf-data/` и упакуйте чарт. Секретный ключ для `nelm chart pack` не нужен.

TypeScript-чарт при упаковке пересобирается, для чего нужен доступ к сети для скачивания его модулей. Чтобы вместо этого использовать собранный TypeScript-код скачанного чарта, передайте `--ts-no-rebuild`.

Чарт, опубликованный werf 3.12 и более ранними версиями, тоже можно переупаковать: `nelm chart pack` переносит его `extra_annotations.json` и `extra_labels.json` в `.werf-data/`, а его `values.yaml`, содержащий объединённые при публикации параметры, остаётся собственным `values.yaml` чарта.

Вместо `nelm chart pack` и `nelm chart upload` можно использовать `helm package` и `helm push`: они сохраняют `.werf-data/`, если её не исключает `.helmignore` чарта.

## Изменение версии опубликованного чарта

Для изменения тега уже опубликованного чарта скопируйте бандл с новым тегом с помощью команды `werf bundle copy`, например:

```shell
werf bundle copy --from example.org/bundles/mybundle:v1.0.0 --to example.org/bundles/renamedbundle:v2.0.0
```

`werf bundle copy --to REPO:TAG` задаёт версию копии по `TAG` по [тем же правилам](#имя-и-версия-чарта), что и `werf bundle publish`, и публикует копию с тегом версии и указанным тегом. `werf bundle copy --to REPO` без тега сохраняет версию и тег исходного чарта. Копия называется по последнему компоненту пути целевого репозитория.

## Копирование бандла в другой репозиторий

Для удобного копирования бандла в другой репозиторий имеется команда `werf bundle copy`. Кроме непосредственного копирования чарта и связанных с ним образов эта команда также заново формирует ссылки на образы в `.werf-data/extra-values.yaml` и в аннотации `helm.sh/images` для целевого репозитория.

Пример:

```shell
werf bundle copy --from example.org/bundles/mybundle:v1.0.0 --to other.example.org/bundles/mybundle:v1.0.0
```

Ссылки на образы в опубликованном werf чарте, подключённом как зависимый, не переписываются: он сохраняет ссылки на свой исходный репозиторий.

Подписанный чарт (с provenance-файлом Helm) сохраняет подпись при копировании без изменений. Если при копировании чарт меняется, например, переписываются ссылки на образы, меняется имя или версия, подпись удаляется с предупреждением.

`werf bundle apply`, `werf bundle plan` и `werf bundle render` проверяют подпись бандла, скачанного из container registry, по публичным ключам из `--provenance-keyring`, если передан `--provenance-strategy=verify` (бандл без подписи вызывает ошибку) или `--provenance-strategy=verify-if-possible` (проверяется только подписанный бандл). `werf bundle render --bundle-dir` не может проверить подпись распакованного бандла и с `--provenance-strategy=verify` завершается ошибкой.

## Экспорт бандла из container registry в архив

После публикации бандл может быть экспортирован из репозитория в локальный архив для дальнейшей дистрибуции иными способами с помощью команды `werf bundle copy`, например:

```shell
werf bundle copy --from example.org/bundles/mybundle:v1.0.0 --to archive:archive.tar.gz
```

## Импорт бандла из архива в репозиторий

Экспортированный в архив бандл можно снова импортировать в тот же или другой OCI-репозиторий командой `werf bundle copy`, например:

```shell
werf bundle copy --from archive:archive.tar.gz --to other.example.org/bundles/mybundle:v1.0.0
```

После этого вновь опубликованный бандл (чарт и его образы) снова можно использовать привычными способами.

## Использование чарта с Helm, Argo CD и Flux

Helm, Argo CD и Flux устанавливают опубликованный чарт с его собственным `values.yaml` и параметрами, переданными им при установке. Сами они не читают `.werf-data/`, поэтому ссылок на образы и параметров, переданных `werf bundle publish`, у них нет: шаблоны, использующие `.Values.werf.image.*` или `.Values.global.werf.images.*`, получают пустые ссылки.

> **Примечание**: в чартах, опубликованных werf 3.12 и более ранними версиями, ссылки на образы и опции `--values` и `--set*` команды `werf bundle publish` объединялись в `values.yaml`. В новых чартах этого нет, поэтому для развёртывания нового чарта через Helm, Argo CD или Flux нужны файлы параметров, описанные ниже.

`.werf-data/values.yaml` (`--values` команды `werf bundle publish`) и `.werf-data/extra-values.yaml` (ссылки на образы и другие служебные параметры werf) — обычные YAML-файлы внутри чарта, поэтому их можно передать как файлы параметров.

Flux, `HelmRelease`, чарт которого берётся из `HelmRepository` типа `oci`:

```yaml
spec:
  chart:
    spec:
      chart: mybundle
      sourceRef:
        kind: HelmRepository
        name: bundles
      valuesFiles:
        - values.yaml
        - .werf-data/values.yaml
        - .werf-data/extra-values.yaml
```

`valuesFiles` заменяет список файлов параметров по умолчанию, поэтому `values.yaml` нужно указать первым.

Argo CD, пути указываются относительно корня чарта:

```yaml
spec:
  source:
    repoURL: example.org/bundles
    chart: mybundle
    targetRevision: 1.0.0
    helm:
      valueFiles:
        - .werf-data/values.yaml
        - .werf-data/extra-values.yaml
```

Даже с этими файлами параметров в Helm, Argo CD и Flux недоступно следующее:

* опции `--set*` команды `werf bundle publish`;
* секреты: Helm не может расшифровать `secret-values.yaml`, `.werf-data/secret-values.yaml` и файлы `secret/`, а шаблоны, вызывающие `werf_secret_file`, завершаются ошибкой;
* аннотации и лейблы `werf bundle publish`;
* `--disable-default-values` команды `werf bundle publish`: Helm по-прежнему использует `values.yaml` чарта;
* ресурсы, генерируемые TypeScript: Helm не выполняет `ts/`;
* всё из `.werf-data/`, если опубликованный werf чарт — зависимый чарт чарта, развёртываемого через Helm, Argo CD или Flux.

Helm помещает `.werf-data/` в `.Files` и сохраняет её в релизе вместе с остальным чартом (`.werf-data/secret-values.yaml` остаётся зашифрованным). Шаблоны, читающие все файлы чарта, например через `.Files.Glob "**"`, получают и файлы `.werf-data/`.

## Совместимость с другими версиями werf и Nelm

Чарты, опубликованные werf 3.12 и более ранними версиями, текущая версия werf развёртывает без изменений.

Текущий формат чарта (`apiVersion: v2` в `.werf-data/metadata.yaml`) требует werf v3 или Nelm v2 с поддержкой `.werf-data/`. Последние версии werf v2 и Nelm v1 отказываются развёртывать такой чарт, а также чарт, подключающий его как зависимый. Более ранние версии werf v2 и Nelm v1, werf 3.12 и более ранние версии, а также версии Nelm v2 без поддержки `.werf-data/` не отказываются: они развёртывают чарт только с его собственными параметрами, без ссылок на образы, параметров, секретов, аннотаций и лейблов `werf bundle publish`.
